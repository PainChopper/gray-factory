Примеры показывают возможные риски, а не готовые замечания: каждый риск должен подтверждаться проверяемым кодом.

# Ошибки

- Если изменённый вызов возвращает `error`, проследи её обработку или передачу выше. Для проигнорированной ошибки покажи конкретное последствие.
- Проверь, не подменяют ли `panic` и `recover` возврат обычной ошибки. Объясни, где вызывающий код теряет возможность обработать сбой; сам по себе `panic` не считай дефектом.
- Если вызывающий код различает ошибки по типу или значению, проверь, сохраняет ли новая обёртка это различие через `errors.Is` или `errors.As`.
- Если рабочий код выбирает действие по тексту `err.Error()`, укажи зависимую ветку как дефект и предложи проверку через `errors.Is`, `errors.As` или явный код ошибки.
- Если функция обозначает неудачу обычным значением (`""`, `0`, `nil`), проверь, может ли оно быть допустимым результатом. При неоднозначности покажи, где вызывающий код неверно трактует результат, и предложи отдельный `error` или `ok`.

Пример риска для обёртки и проверки текста (адаптирован по [разбору ошибок команды Go](https://go.dev/blog/go1.13-errors#whether-to-wrap)):

```go
var ErrNotFound = errors.New("not found")

func findUser(id string) error {
    if err := lookup(id); err != nil {
        return fmt.Errorf("lookup user: %v", err)
    }
    return nil
}

func responseCode(id string) int {
    err := findUser(id)
    if err == nil {
        return http.StatusOK
    }
    if err.Error() == ErrNotFound.Error() {
        return http.StatusNotFound
    }
    return http.StatusInternalServerError
}
```

Последствие: если `lookup` вернёт `ErrNotFound`, обёртка оставит только текст `lookup user: not found`; сравнение не сработает, и вместо 404 получится 500. Исходная ошибка также станет недоступна для `errors.Is`. Само по себе применение `%v` не является дефектом, если вызывающему коду не нужна исходная ошибка.

Пример риска (адаптирован по [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments#in-band-errors)):

```go
func Lookup(m map[string]string, key string) string {
    return m[key]
}

func Found(m map[string]string, key string) bool {
    return Lookup(m, key) != ""
}
```

Последствие: существующая запись с пустым значением будет принята за отсутствующую.

# Контекст и конкурентность

- Для новой операции, зависящей от запроса, проверь передачу `context.Context` до вызываемых операций. Если имеющийся контекст заменён на `context.Background()`, укажи, где теряются отмена или срок выполнения. Для нового производного контекста проверь вызов `cancel`.

Пример риска (адаптирован по [документации Go об отмене операций](https://go.dev/doc/database/cancel-operations)):

```go
func firstUser(r *http.Request, db *sql.DB) (string, error) {
    var name string
    err := db.QueryRowContext(context.Background(), "SELECT name FROM users LIMIT 1").Scan(&name)
    return name, err
}
```

Последствие: отмена входящего запроса не дойдёт до запроса к БД; он может продолжить работу после ухода клиента.

- Для новой горутины найди условие завершения и реакцию на отмену. Отмечай путь, на котором она навсегда ждёт канал или продолжает работу после завершения запроса.

Пример риска (адаптирован по [Go Concurrency Patterns](https://go.dev/blog/pipelines#stopping-short)):

```go
result := make(chan int)
go func() { result <- work() }()

select {
case value := <-result:
    use(value)
case <-ctx.Done():
    return
}
```

Последствие: если запрос отменится раньше отправки результата, получать из канала будет некому и горутина навсегда заблокируется на отправке.

- При доступе нескольких горутин к изменяемому состоянию проверь синхронизацию и копирование уже использованных значений `sync`. Само наличие состояния пакета или `sync.Once` не является дефектом.

Пример риска (адаптирован по [документации `sync.Mutex`](https://pkg.go.dev/sync#Mutex) и [Go maps](https://go.dev/blog/maps)):

```go
type Cache struct {
    mu   sync.Mutex
    data map[string]int
}

func (c Cache) Put(key string, n int) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.data[key] = n
}
```

Последствие: каждый вызов запирает свою копию `Mutex`, но записывает в общую `map`; параллельные записи остаются незащищёнными.

# API и значения

- При изменении экспортируемого API или интерфейса проследи вызовы и реализации, включая набор методов указателя и значения. Замечание обоснуй конкретной несовместимостью.
- Проверь запись в потенциально `nil`-map и различие между `nil` и пустым срезом там, где оно меняет контракт, например `null` и `[]` в JSON. Не требуй ненулевого среза по умолчанию.
- Если код создаёт ключ, токен или иной секрет, проверь источник случайности: для этого нужен `crypto/rand`, а не `math/rand`.

# Ресурсы

- Для открытых файлов, тел HTTP-ответов и других `io.Closer` проследи закрытие на всех путях выхода. Если закрытие завершает запись, проверь, не теряется ли его ошибка.

# База данных

- Если Go-код формирует SQL, проверь, что значения внешнего ввода передаются параметрами. Динамические имена таблиц, столбцов и порядок сортировки должны выбираться из ограниченного набора.
- Для запросов с набором строк проверь закрытие `Rows`, ошибки `Scan` и `Rows.Err()`.
- Если запрос ищет одну строку, проверь, отличается ли «не найдено» (`sql.ErrNoRows` для `database/sql`) от технической ошибки там, где это меняет поведение.
- Если несколько зависимых операций должны быть атомарны, проверь, что они выполняются через одну транзакцию и каждая ветвь доходит до `Commit` или `Rollback`.

# Идиоматичность

- Обоснованное замечание из этого раздела требует исправления и результата `CHANGES_REQUIRED`: покажи место и конкретную пользу исправления. Косметические мелочи без заметной пользы не отмечай.
- Предлагай ранний возврат при ошибке, когда он заметно проясняет основной путь вместо глубокой вложенности.
- Для нового интерфейса найди его потребителя. Если ему достаточно конкретного типа, укажи на лишнюю абстракцию; если интерфейс нужен, оцени, не проще ли определить его у потребителя.
- Для нового пакета или экспортируемого имени проверь, понятно ли сочетание `pkg.Name` в месте вызова. Замечание о неясном имени или повторе имени пакета выноси, только если это мешает чтению кода.
- Для нового экспортируемого API проверь, объясняют ли комментарии его назначение и важные для вызывающего кода условия, а не просто повторяют имя.
- Для нового типа проверь, можно ли использовать его нулевое значение. Если нужна инициализация, проверь, понятны ли конструктор или обязательное условие использования; не требуй пригодного нулевого значения от каждого типа.
- Для новых методов проверь выбор получателя-значения или получателя-указателя: изменяемость, копирование и набор методов. Непоследовательность отмечай только с конкретным последствием.

# Go-тесты

- Сопоставь изменённое поведение с тестами как с текстом: отметь конкретные непроверенные ветки, ошибки или граничные случаи, не навязывая форму теста.
- В изменённых тестах проверь зависимость от порядка, времени, случайности и общего состояния.
- Если тест сравнивает точный текст ошибки, проверь, что он проверяет именно сообщение. Иначе предложи проверку самого факта ошибки или её типа/значения.
