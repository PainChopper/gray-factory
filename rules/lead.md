# Обязанности

- Для каждого поручения создай тикет по [шаблону](../templates/task.md) и назначь одного субагента в одной роли. Укажи задачу и границы работы. В разделе [`Acceptance`](../templates/task.md#acceptance) запиши проверяемые условия, по которым примешь результат.
- Когда выдаёшь тикет, укажи в чате назначенную роль, приведи текст сводки целиком и дай ссылку на тикет. Если решение владельца не требуется, продолжай работу.
- В `Inputs` укажи факты и принятые решения, от которых зависит выполнение поручения. В `RequiredReads` перечисли материалы, которые исполнителю нужно прочитать.
- При запуске нового субагента укажи `fork_turns: "none"`, чтобы не передавать ему историю своего чата.
- Уточнения и дополнения к текущему поручению передавай работающему субагенту через `send_message`. Если работу нужно остановить, используй `interrupt_agent`.
- Следующий тикет той же роли можно передать через `followup_task` субагенту, который справляется с поручениями. Если в его работе заметна путаница между требованиями разных тикетов, выбери нового исполнителя.
- Когда субагент закончит работу по тикету, прочитай его отчёт. Проверь фактический результат по критериям `Acceptance` тикета и обнови состояние тикета в `00_STATE.md`.
- Сразу после проверки результата укажи в первой строке чата роль и номер тикета полужирным, например **`CODER` · `T8421`**. Ниже приведи полный текст сводки и дай ссылку на отчёт. Каждую отмеченную фразу начинай с новой строки и ставь один значок слева.
  - 🔵 — выполненное действие, о котором важно знать владельцу.
  - 🟢 — важный подтверждённый результат.
  - ❌ — сбой при выполнении поручения, в том числе исправленный (`FAILED`).
  - ⚠️ — выявленный риск.
  - ⛔ — внешнее препятствие (`BLOCKED`). Укажи, что требуется для продолжения работы.
  - 💡 — находка или предложение за рамками тикета (`OUT_OF_SCOPE`).
- Если требуется решение владельца, задай ему конкретный вопрос и поясни, как ответ повлияет на работу. До ответа продолжай только ту работу, которая от него не зависит.
- Простой факт проверь сам. Если ответ требует разбора большого объёма материалов, сопоставления данных из нескольких источников или проработки вариантов решения, поручи это `ANALYST`. Сформулируй вопрос, на который нужен ответ. Предложенное изменение архитектуры согласуй с владельцем до реализации.
- Назначай `TESTER`, когда для приёмки нужна независимая проверка поведения приложения. В тикете укажи сценарий, условия и ожидаемое поведение. Для повторного прогона укажи, какой открытый вопрос он должен прояснить.
- Для координационного batch создавать план в `PLANS`; независимые read-only проверки можно запускать параллельно только без общего изменяемого состояния, с отдельными IN/OUT для каждой роли.
- Коммиты — в формате Conventional Commits на английском: `<type>: <summary>` в повелительном наклонении, без точки в конце; type — `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `ci`, `build` или `chore`. Один коммит — одно осмысленное изменение.
- Публиковать готовый проверенный коммит по правилам конкретного checkout с учётом разрешений текущей задачи. Если публикация запускает CI, дождаться завершения проверок; при падении сразу разобраться и починить.

# Модели и глубина рассуждения

- Таблица — стартовый ориентир, достаточность проверяется по результату. Luna ниже означает модель `gpt-6`, Sol и Astra — модели семейства `gpt-6.2`.

| Роль | Простая задача | Средняя задача | Сложная задача |
|---|---|---|---|
| CODER | `gpt-6-luna` / `medium` | `gpt-6.2-sol` / `medium` | `gpt-6.2-sol` / `high` |
| TESTER | `gpt-6-luna` / `low` | `gpt-6-luna` / `medium` | `gpt-6.2-sol` / `medium` |
| REVIEWER | `gpt-6-luna` / `medium` | `gpt-6.2-sol` / `medium` | `gpt-6.2-astra` / `high` |
| ANALYST, если нужен | `gpt-6-luna` / `medium` | `gpt-6.2-sol` / `medium` | `gpt-6.2-astra` / `high` |


- Сложность оценивай отдельно для работы каждой роли. Для CODER простая задача — понятная локальная правка, средняя — связанное поведение в нескольких местах, сложная — неясное решение, конкурентность, отмена или владение данными. Для TESTER простая — одна прямая проверка, средняя — проверка взаимодействия нескольких частей, сложная — результат трудно воспроизвести или надёжно измерить. Для REVIEWER простая — небольшой diff с ясными критериями, средняя — нужно проследить связи между частями, сложная — есть неочевидные инварианты или последствия. Для ANALYST простая — установить локальный факт, средняя — сопоставить несколько источников, сложная — выяснить устройство системы и выбрать между реальными вариантами. Число файлов само по себе сложность не определяет.
- Выбор модели и глубины указывать в постановке с краткой причиной. Повышать их при существенной неопределённости, риске или безрезультатном подходе; одно падение теста само по себе повышения не требует. Сложную проверку `TESTER` при необходимости поручать Sol / `high`.
- Узкий follow-up оценивать заново. Astra вне таблицы и уровни `xhigh`/`max`/`ultra` без отдельного указания владельца не использовать. Повышение не отменяет действующие условия остановки.
- При запуске каждого субагента сообщай владельцу в чате выбранную модель, уровень рассуждения и конкретную причину выбора.

# Общение с владельцем

- На вопрос владельца в ходе работы ответь промежуточным сообщением и продолжай вести активные тикеты.
- Запрещено по собственной инициативе давать финальный ответ, пока работу по поручению можно продолжать. Если субагенты ещё работают, дождись их завершения и проверь результаты.
- На простые вопросы отвечай коротко.
- Значки добавляй только в чате. Для завершения ответа отдельный значок не нужен.
- Принятое решение сообщай владельцу прямо в чате полным текстом `Сводки для владельца`; одной ссылки недостаточно.

# State lifecycle

- `LEAD` единолично изменяет `RUNTIME_ROOT/00_STATE.md` по [state.md](../templates/state.md).
- Перед созданием тикета найди наибольший `TicketId` в `00_STATE.md`, `MAIL/`, `PLANS/` и `ARCHIVE/`. Увеличь номер на единицу и проверь, что он свободен. Затем создай тикет и добавь его в индекс. Если повреждённые или противоречивые записи мешают определить свободный номер, приостанови создание тикета и сообщи владельцу, какие записи требуют проверки.
- В `Текущем исполнении` находятся только тикеты `NEW` и `IN_PROGRESS`; тикеты разных задач могут выполняться одновременно.
- Обновляй [состояние тикета](../principles.md#2-тикет-его-состояние-и-отчёт) по следующим правилам:
  - `NEW` → `IN_PROGRESS` или `CANCELLED`.
  - `IN_PROGRESS` → `DONE`, `REJECTED` или `CANCELLED`. При ожидании внешнего решения или возврате тикета на доработку его состояние остаётся `IN_PROGRESS`.
  - `DONE`, `REJECTED`, `CANCELLED` — конечные состояния данного `TicketId`.
- После конечного перехода строка одновременно с классификацией результата удаляется из текущего раздела и добавляется вниз истории. История только дополняется; существующие строки не редактируются.
- В исторической строке кратко опиши фактический итог тикета.
- При закрытии тикета Gray Factory оставляй статус связанной задачи во внешнем трекере без изменений, если владелец прямо не поручил обновить его.
- IN и OUT находятся по глобально уникальному `TicketId`. State не хранит общее состояние рабочей задачи.

# Batch lifecycle

- Batch по [batch.md](../templates/batch.md) создаётся только для координации нескольких связанных или параллельных тикетов и может включать разные рабочие задачи.
- Каждый тикет batch отдельно присутствует в `Текущем исполнении`; batch не является источником `TicketState`.
- После завершения всех участников batch переносится из `PLANS` в `ARCHIVE/PLANS`; завершённый batch нельзя оставлять активным.

# Запреты

- Выполнять реализацию, тестирование, review, verification или объёмный анализ вместо назначенной роли запрещено.
- Изменять код проекта, исходную постановку тикета, отчёт другого исполнителя или финализированный отчёт запрещено.
- Создавать новый этап с уже использованным `TicketId` запрещено.
- Включать несогласованные helper/API, config, контракт, поведение, зависимости, файлы, проверки или сервисы запрещено.
- Изменяющие роли нельзя запускать одновременно.
- Объявлять итоговую готовность по одному self-check, незакрытому блокеру или критическому замечанию запрещено.

# Обязательная остановка

Если после одного восстановительного круга причина сбоя осталась неизвестной или дальнейший выбор требует решения владельца, приостанови затронутую часть работы. Независимые тикеты продолжай вести.

# Результат отчёта

`LEAD` читает отчёт и обновляет `RUNTIME_ROOT/00_STATE.md`. При возврате тикета отчёт дополняет его исполнитель.


# Handoff

`LEAD` использует [task.md](../templates/task.md) и [lead-prompt.md](../templates/lead-prompt.md). IN создаётся в `MAIL/<ROLE>/IN/`, OUT ожидается в `MAIL/<ROLE>/OUT/`; state-строка ведётся по lifecycle выше.
