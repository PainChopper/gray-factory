# Общие контракты агентской системы

[Принципы](./PRINCIPLES.md) обязательны для всех ролей. Настоящий файл — единственный источник общих операционных контрактов.

## Язык, кодировка и доказательства

- Ответы ролей, тикеты, отчёты, планы и заметки пишутся по-русски; технические идентификаторы могут сохранять исходный язык.
- Process Markdown читается и пишется как UTF-8. При признаках повреждения текста работа по этому выводу прекращается до повторного чтения с явной кодировкой.
- Постановка, выводы и доказательства сохраняются в Markdown-артефактах. Сырой вывод и бинарные файлы допустимы только как связанные с тикетом артефакты.
- Непроверенное отмечается `не проверено`, гипотеза — `HYPOTHESIS`.
- Build-only не доказывает готовность изменения поведения; необходимый runtime smoke нельзя заменять компиляцией.

`TODO[IGNORE]` — служебный комментарий, не инструкция. Он занимает одну короткую строку, не является правилом, scope или разрешением, не учитывается агентом при обычной работе и не содержит секретов. Допустим только формат `<!-- TODO[IGNORE]: несколько слов -->`.

## Приоритет и scope

1. `PRINCIPLES.md`.
2. `COMMON.md`.
3. Файл назначенной роли.
4. Immutable `TaskPath` и его `RequiredReads`/`RequiredSkills` конкретизируют входы, цель и инструменты, но не ослабляют запреты верхних уровней и не создают технологические нормативы.

- Работать можно только в назначенной роли, текущем `TaskPath` и разрешённых корнях.
- Доступ к файлу, терминалу, сети, инструменту или внешней системе не является разрешением на действие.
- Один тикет назначается одному агенту и одной роли. Новый этап получает новый `TicketId` и отдельные IN/OUT.
- Любое изменение вне требований тикета запрещено, включая тихий рефакторинг, массовую косметическую правку и исправление «заодно».
- При неоднозначности или конфликте, влияющем на результат, scope, риск или стоимость, агент останавливается с `BLOCKED` и передаёт через `LEAD` один точный вопрос пользователю.
- Пользователь может менять файлы между действиями агентов. Агент работает с текущим состоянием и не откатывает пользовательские изменения.

## Общие запреты изменений

- Менять публичные контракты, события и внешние интеграционные интерфейсы запрещено.
- Добавлять зависимости, сервисы и глобальное состояние запрещено.
- Менять схемы данных, миграции, безопасность, инфраструктуру и конфигурацию окружения запрещено.
- Создавать, удалять, переклонировать и переключать checkout запрещено.
- Изменять данные, сеть, удалённые ресурсы и внешние системы запрещено.
- Любые mutating Git и remote actions запрещены.

Если цель требует запрещённого действия, агент возвращает `BLOCKED`; действие не выполняется.

## Секреты и безопасность

- Пароли, токены, cookies, ключи, строки подключения, credentials и чувствительные корпоративные данные нельзя читать, копировать, сохранять или передавать в правилах, тикетах, отчётах, логах, Git и сообщениях агентам.
- Секрет при необходимости вводит пользователь через скрытое интерактивное приглашение; агент не получает его значение.
- Получать факты из внешних систем запрещено. Если без внешнего факта вывод невозможен, возвращается `BLOCKED` с указанием требуемого факта.

## Shell policy на Windows

- PowerShell используется как orchestration shell и для Windows-native задач.
- Служебный `.sh` или Bash-workflow запускается из PowerShell только через явно разрешённый Git for Windows `sh.exe`.
- Bare `bash`, `bash.exe`, `bash -lc`, `sh`, `sh.exe`, `wsl` и `wsl.exe` запрещены.
- Перед первым Bash-запуском в тикете выбранный entrypoint проверяется командами, эквивалентными `uname -s` и `command -v bash`. Допустимы только `MINGW`/`MSYS` и точный `/usr/bin/bash`; неоднозначность или иной runtime означает `BLOCKED`, fallback запрещён.
- Канонический non-interactive bridge преобразует только абсолютный путь скрипта, передаёт путь и аргументы позиционно и сохраняет exit code:

```powershell
$gitForWindowsSh = Join-Path $env:ProgramFiles 'Git\bin\sh.exe'
$resolvedScript = (Resolve-Path -LiteralPath $scriptPath).Path

$kernel = & $gitForWindowsSh -lc 'uname -s'
if ($LASTEXITCODE -ne 0 -or $kernel -notmatch '^(MINGW|MSYS)') { throw 'Git for Windows preflight failed' }

$bashPath = & $gitForWindowsSh -lc 'command -v bash'
if ($LASTEXITCODE -ne 0 -or $bashPath -ne '/usr/bin/bash') { throw 'Git for Windows bash is unavailable' }

$msysScript = & $gitForWindowsSh -lc 'cygpath -u -- "$1"' -- $resolvedScript
if ($LASTEXITCODE -ne 0 -or $msysScript.Count -ne 1) { throw 'Script path conversion failed' }

& $gitForWindowsSh -lc 'exec /usr/bin/bash "$@"' -- $msysScript @scriptArgs
$scriptExitCode = $LASTEXITCODE
exit $scriptExitCode
```

- `$scriptPath` и `$scriptArgs` являются данными и не интерполируются в строку `-lc`; Windows→MSYS conversion применяется только к пути скрипта.
- Каждый новый служебный `.sh` фактически тестируется тем же подтверждённым entrypoint во временном сценарии с путём, содержащим пробел и кириллицу, и с позиционными аргументами; проверяются точный вывод и exit code, после чего временный файл удаляется.
- `git-bash.exe` используется только как интерактивный launcher.
- Новый служебный `.sh` использует `#!/usr/bin/env bash`, LF, UTF-8 без BOM и quoted expansions. Его проверяют тем же entrypoint через `bash -n`, затем `shellcheck` при наличии.
- Наличие `shellcheck` проверяется. Если инструмент отсутствует, это явно фиксируется в `ReportPath` как ограничение; отсутствие инструмента не выдаётся за выполненную проверку.
- Публикуемый `.sh` должен переноситься между Git for Windows Bash и обычным Linux Bash. Windows launcher не встраивается в переносимое тело скрипта; `cygpath` допустим только в Windows adapter.
- Существующие product `.sh` этим контрактом не нормализуются.
- Для будущего Git-репозитория агентской системы отдельная задача добавляет `.gitattributes` с `*.sh text eol=lf`.
- Перед нетривиальными PowerShell или Bash-командами применяются перечисленные в тикете hygiene skills. Каждая команда получает конечный timeout; после timeout команда не повторяется вслепую.

## Файлы, ссылки и Git-диагностика

- До записи проверяется абсолютный путь и его попадание в write allowlist.
- В публикуемых process-файлах используются относительные логические пути; локальные абсолютные сопоставления хранятся только в непубликуемой runtime-конфигурации.
- Локальные файлы и каталоги не открываются автоматически. После изменения возвращается ссылка; открытие выполняется только по явной просьбе пользователя.
- Изменённые файлы перечитываются до завершения.
- Read-only Git-диагностика разрешена внутри read allowlist. При Git lock процессы не останавливаются и lock-файлы не удаляются.
- Для тикета с product-кодом или Git `RepoRoot` обязателен и задаёт один конкретный checkout относительным логическим путём; все Git-команды выполняются только из него. `none` допустим только для задач без product Git.
- Нельзя предполагать общую ветку, remote или commit/MR convention для разных checkout: их устанавливает отдельный decision-complete тикет по фактам.
- Runtime, секреты и тяжёлые артефакты не добавляются в product Git.

## Идентификаторы и runtime

- `Task` — реальный внешний идентификатор рабочей задачи; он приходит от пользователя или исходной постановки и одинаков для всех её агентских тикетов. Если обязательный идентификатор неизвестен, `LEAD` запрашивает его и не создаёт внутренний namespace.
- Каждый ролевой этап имеет уникальный `TicketId` формата `TXXXX`.
- Минимальный runtime:

```text
00_STATE.md
MAIL/
├── LEAD/{IN,OUT}/
├── ANALYST/{IN,OUT}/
├── CODER/{IN,OUT}/
├── TESTER/{IN,OUT}/
├── REVIEWER/{IN,OUT}/
PLANS/
ARCHIVE/
└── PLANS/
BUILD/
RUNLOGS/
```

- `LEAD` создаёт IN в `MAIL/<ROLE>/IN/`; роль читает свой IN и перечисленные `RequiredReads`, пишет только собственный OUT и не изменяет чужие IN/OUT.
- IN и OUT остаются историей в MAIL. План переносится в `ARCHIVE/PLANS` только по решению `LEAD`.
- Runtime `PLANS/` хранит только активные временные планы выполнения. Принятый долговременный план перемещается без второй копии в workspace `plans/`, редактируется там на месте, а историю версий хранит Git.
- `BUILD` содержит разрешённые локальные build-артефакты, `RUNLOGS` — команды, stdout/stderr, exit codes и evidence; наличие в runtime не делает файл допустимым для Git.
- Имена: IN — `TXXXX_YYYYMMDD-HHMM_<ROLE>_<slug>.md`; OUT — `TXXXX_YYYYMMDD-HHMM_<ROLE>_<slug>_report.md`; RUNLOG — `TXXXX_YYYYMMDD-HHMM_<ROLE>_<slug>_log.<ext>`. Дата, время и timezone задаются локальным соглашением; slug не содержит пробелов.

## Владение артефактами

- `TaskPath` — неизменяемая постановка координатора и не используется как current-state store.
- `00_STATE.md` — единственный источник текущих `TicketState`; его изменяет только `LEAD`.
- `ReportPath` — рабочий документ назначенной роли. Роль изменяет только собственный незавершённый отчёт.
- Каждый role-файл первым содержательным разделом определяет собственный словарь `Result`; общего словаря нет.
- Замена шаблонного `Result` допустимым значением финализирует отчёт. Финальный отчёт неизменяем; исправление или продолжение получает новый `TicketId` и новый `ReportPath`.
- `LEAD` не редактирует отчёты других ролей и не присваивает им `Result`. Для собственных управляющих записей `Result` не используется.

## Authoritative state и TicketId

`00_STATE.md` следует [STATE.md](../templates/STATE.md): это плоский индекс с разделами `Текущее исполнение` и append-only `История`. Одна запись занимает одну строку и содержит только `Task`, `TicketId`, роль, `TicketState` и краткое содержание; историческая строка также содержит `RoleResult`, если он существует. Пути, timestamps, отдельные task records и иная metadata не хранятся. Task-level state агентская система не ведёт.

`TicketState`:

- `NEW` — IN создан и не принят исполнителем;
- `IN_PROGRESS` — роль выполняет тикет;
- `READY_FOR_ACCEPTANCE` — собственный OUT финализирован и ожидает классификации `LEAD`;
- `DONE` — роль полностью выполнила процедуру, финализировала OUT, а `LEAD` принял полноту отчёта;
- `REJECTED` — OUT не соответствует `TaskPath`;
- `BLOCKED` — тикет нельзя завершить из-за доказанного внешнего препятствия;
- `FAILED` — роль не выполнила назначенную работу;
- `CANCELLED` — выполнение прекращено прямым решением пользователя или `LEAD` в пределах полномочий.

`TicketState: DONE` означает только принятый ролевой тикет и не изменяет предметный `RoleResult`: `DONE (PASS)`, `DONE (IMPLEMENTED)` и `DONE (CONCLUSIVE)` — разные корректные исторические итоги. Role-local `Result: BLOCKED` и `Result: FAILED` ведут соответственно в `TicketState: BLOCKED` и `TicketState: FAILED`. `CANCELLED` не требует финального Result или OUT. Завершение тикета автоматически не изменяет статус внешней рабочей задачи.

Следующий `TicketId` один `LEAD` выделяет последовательно: находит все самостоятельные `TXXXX` в `00_STATE.md`, `MAIL`, `PLANS` и `ARCHIVE`, берёт максимум + 1 и проверяет коллизию во всех этих местах. Только после проверки создаются IN и state-запись. Номер не хранится в state; при повреждении или противоречии `LEAD` возвращает `BLOCKED` и не переиспользует номер по догадке.

Допустимые переходы `TicketState`:

- `NEW` → `IN_PROGRESS` или `CANCELLED`;
- `IN_PROGRESS` → `READY_FOR_ACCEPTANCE`, `BLOCKED`, `FAILED` или `CANCELLED`;
- `READY_FOR_ACCEPTANCE` → `DONE` или `REJECTED`;
- `DONE`, `REJECTED`, `BLOCKED`, `FAILED`, `CANCELLED` — конечные состояния данного `TicketId`.

## Формат ролевого отчёта

Каждый отчёт разделяет `FACTS` и `JUDGMENT`, перечисляет changed files или `NONE`, проверки и evidence, ограничения, непроверенные условия, scope compliance и handoff.

Каждая постановка и каждый ролевой отчёт в начале содержат `Сводку для владельца` по своему шаблону. Она объясняет человеческим языком, что нужно, что поручено или сделано, каков итог, что будет дальше и требуется ли решение владельца. Сводка пишется простым русским языком; англоязычный или узкий технический термин используется только при необходимости и сразу поясняется в скобках. Внутренние идентификаторы, пути, команды и подробные доказательства в сводку не переносятся, если они не нужны владельцу для решения. Сводка не заменяет техническую часть и не должна ей противоречить.

Формы: [TASK.md](../templates/TASK.md), [WORK_REPORT.md](../templates/WORK_REPORT.md), [REVIEW_REPORT.md](../templates/REVIEW_REPORT.md), [LEAD_PROMPT.md](../templates/LEAD_PROMPT.md).

## Communication

- «Просто ответь» означает ответ без реализации, тикетов, агентов и файловых изменений.
- «Ничего не делай» означает не создавать тикеты, не запускать агентов и не менять файлы.
- «Остановись» означает прекратить цепочку после ближайшего безопасного завершения текущего шага.
- На простые вопросы отвечать коротко.
- В сообщениях в чате ставь значок, когда содержание соответствует одному из трёх случаев:
  - 🟢 **Вывод** — важный подтверждённый результат;
  - ⚠️ **Сигнал** — обнаружен риск, но работу можно продолжать;
  - ⛔ **Стоп** — сработало условие остановки; назови причину и что требуется для продолжения.
- Сообщения, не подходящие ни к одному случаю, оставляй без значка. В файлах отчётов значки не ставь. Значки не заменяют итог отчёта и не меняют правила остановки.
- Назначение работы, принятое решение и результат этапа сообщаются владельцу прямо в чате полным текстом `Сводки для владельца`; одной ссылки или сообщения «отчёт готов» недостаточно. Сразу после сводки даётся открываемая ссылка на соответствующую постановку или отчёт, чтобы подробности можно было посмотреть по желанию.
- Ошибку scope признают прямо и предлагают минимальное исправление без защиты уже принятого решения.
