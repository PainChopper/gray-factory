# Наши правила Go для CODER

Накопительный файл для правил, согласованных при разборе кода. Добавляем новые пункты по мере необходимости; общие Go-навыки используем как справочники, а не как готовые правила проекта.

## Ошибки

- Проверяй ошибку рядом с вызовом. Если контракт вызова допускает полезный результат вместе с ошибкой, как `Read` с `n > 0`, обработай результат до проверки конца файла.
- Когда от вызова нужна только ошибка, предпочитай `if err := call(); err != nil { ... }`: у каждой проверки свой локальный `err`.
- Когда результат нужен дальше, используй `value, err := call()` и проверяй `err` сразу после вызова.
- Называй обычную локальную ошибку `err`. После проверки предыдущей ошибки можно повторно присвоить ей значение в том же блоке либо объявить новый `err` в коротком `if`. Иное имя используй, только когда нужно одновременно различать несколько ошибок; не оставляй ошибку непроверенной перед следующим присваиванием.

## Читаемость

- Пустой строкой разделяй смысловые этапы, а не каждый `if`. Связанные действия держи рядом; не оставляй пустую строку перед закрывающей скобкой без причины.
- Комментируй неочевидную цель или инвариант, а не пересказывай соседнюю строку кода.

## Конфигурация

- Закоммиченный `config.toml` модуля — штатный пример для чистого клона, он работает на выборке из репозитория. Личные значения в него не вносятся.
- Рабочий конфиг владельца на реальных данных лежит вне checkout и передаётся через `--config`. Агенты его не читают и не меняют.
- В тестах одна базовая валидная конфигурация на модуль — хелпер `testConfig()` в `_test.go`, возвращающий готовую структуру. Тест меняет только нужные ему поля; полный конфиг в тесте не прописывается.
- TOML-файлы в `testdata/` — только для тестов разбора и валидации; один файл на случай, имя по случаю.
- Закоммиченный пример проверяет один тест: файл разбирается и проходит валидацию. Точные значения не сверяются.

## Тесты

- Тест читает только закоммиченные и локально неизменяемые файлы: общие фикстуры в `testdata/` и выборку данных из репозитория. Нельзя опираться на то, что у владельца может отличаться от чистого клона: локальные правки конфигов и незакоммиченные данные в `data/`.
- Тест на исправление или новое поведение должен падать без этого изменения. Перед сдачей временно откати правку и убедись, что тест красный; в [отчёте](../templates/coder-report.md) укажи, чем это проверено.
- Проверяй наблюдаемое поведение через контракт пакета, а не внутренние поля и порядок вызовов, если сам порядок не является контрактом.
- Время и конкурентность — через `testing/synctest` и явную синхронизацию, без `time.Sleep` и ожидания «на глаз».
- Однотипные случаи — табличным тестом с `t.Run` и понятными именами случаев; разнородные сценарии — отдельными тестами.
- Ошибки сравнивай через `errors.Is`/`errors.As` или по типу, а не по тексту сообщения, если текст не является контрактом.
- Тест, проверяющий удалённый код или дублирующий другой тест, удаляется вместе с кодом, а не адаптируется.
