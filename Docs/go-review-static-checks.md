# Go: статические проверки для REVIEWER

## Назначение и границы

Это дополнение к [REVIEWER.md](../rules/REVIEWER.md), а не замена его общим правилам. Применять только к изменённому Go-коду и к связанным с ним строкам. Проверка остаётся статической: читать diff и путь использования, не менять материалы и не выполнять код, тесты, сборку или стенд.

Пункт чек-листа — повод искать конкретный дефект, а не норма «по умолчанию». Если из кода не виден риск, замечания нет.

## Общий Go-код

- Для изменённого публичного API или интерфейса проследить вызовы и реализации. Замечание уместно при видимой несовместимости: например, изменённый контракт ошибки, потерянное различие между `nil` и значением, несоответствие method set или несовместимое изменение данных. [Code Review Comments](https://go.dev/wiki/CodeReviewComments)
- Проверить передачу `context.Context` по изменённому пути: он нужен, когда операция зависит от срока, отмены, трассировки или учётных данных. Риск — создать новый фоновый контекст либо не передать имеющийся дальше, из-за чего отмена запроса не дойдёт до операции. [Contexts](https://go.dev/wiki/CodeReviewComments#contexts)
- Проверить все новые и затронутые ошибки на пути до вызывающего кода. Игнорирование ошибки допустимо только если из кода ясно, почему результат безопасен; иначе есть риск продолжить работу с неверным состоянием. [Handle Errors](https://go.dev/wiki/CodeReviewComments#handle-errors)
- Для новых горутин найти условие завершения, владельца и реакцию на отмену. Замечание обосновано, если по статическому пути горутина может навсегда ждать канал или продолжать пользоваться данными после завершения вызывающего кода. [Goroutine Lifetimes](https://go.dev/wiki/CodeReviewComments#goroutine-lifetimes)
- Проверить изменяемое состояние пакета. Классический singleton в Go возможен через состояние пакета и `sync.Once`; само имя паттерна не является проблемой. Замечание нужно при конкретном риске глобального изменяемого состояния: утечке между запросами/тестами, зависимости от порядка вызовов, повторной инициализации или доступе из конкурентных путей без синхронизации. `sync.Once` как раз предназначен для однократного действия. [sync.Once](https://pkg.go.dev/sync#Once)
- Для map, shared-объектов и копирования типов с синхронизацией проверить видимый путь: запись в потенциально nil map приведёт к panic, а копирование использованного `sync`-значения или несинхронизированный конкурентный доступ могут нарушить состояние. Не делать замечание только из-за наличия `nil`, указателя или value receiver. [sync](https://pkg.go.dev/sync), [Copying](https://go.dev/wiki/CodeReviewComments#copying)
- Если изменение создаёт ключ, токен или иной секрет, проверить источник случайности: `math/rand` не подходит для ключевого материала. [Crypto Rand](https://go.dev/wiki/CodeReviewComments#crypto-rand)

## Доступ к БД — только если он затронут

- Проверить, что значения из внешнего ввода передаются как параметры запроса. Если в SQL динамически подставляется имя таблицы, столбца или направление сортировки, из кода должен быть виден ограниченный набор допустимых значений; параметры не заменяют идентификаторы. [Защита от SQL-инъекций](https://go.dev/doc/database/sql-injection)
- Для пути, который уже несёт `context.Context`, проверить контекстный вариант операции. Иначе отмена и дедлайн могут не достичь БД. [database/sql](https://pkg.go.dev/database/sql)
- После `QueryContext`/`Query` проверить жизненный цикл `Rows`: при досрочном выходе они должны закрываться; после обхода нужны обработка ошибок `Scan` и `Rows.Err()`. [Rows](https://pkg.go.dev/database/sql#Rows)
- Проверить соответствие операции API: для изменений данных обычно нужен `Exec`, для одной строки — `QueryRow`/`QueryRowContext`, для набора — `Query`/`QueryContext`. Риск — лишний курсор, неосвобождённые ресурсы или не обработанная ошибка. [Database operations](https://go.dev/doc/database/)
- Если изменяется единая операция из нескольких зависимых записей, проследить границу транзакции: все нужные обращения идут через `Tx`, а у каждой ветви есть `Commit` или `Rollback`. Замечание только при видимом нарушении атомарности или незавершённой транзакции. [Executing transactions](https://go.dev/doc/database/execute-transactions), [Tx](https://pkg.go.dev/database/sql#Tx)
- Проверить обработку `sql.ErrNoRows`, когда «не найдено» и техническая ошибка ведут к разным внешним последствиям. Не навязывать конкретный доменный тип ошибки. [Querying for data](https://go.dev/doc/database/querying)

## Тестовый код — только как текст, если затронут

- Сопоставить изменённое поведение с тестами в diff и рядом: отметить отсутствие статически необходимого примера только когда видны новый контракт, ветвление, ошибка или граничный случай, которые иначе остаются без проверки.
- Проверить, что тест не зависит от нестабильных внешних деталей: времени, случайности, порядка, общего изменяемого состояния, окружения или точных байтов чужой сериализации — если из кода нет изоляции либо контракт не требует именно этих байтов. [Compare Stable Results](https://go.dev/wiki/TestComments#compare-stable-results)
- Если тест проверяет ошибку, предпочитать её семантику, а не текст, когда строка не объявлена частью контракта. Если есть `t.Run`, имя и сообщение при падении должны позволять понять сценарий, вход, `got` и `want`. [Test Error Semantics](https://go.dev/wiki/TestComments#test-error-semantics), [Useful Test Failures](https://go.dev/wiki/CodeReviewComments#useful-test-failures)

## Стандарт доказательства замечания

Каждое замечание должно содержать: точную строку или фрагмент diff, связанный путь вызова/данных, конкретный сценарий, наблюдаемый по коду, и его последствие. Ссылка на источник нужна для правила языка или API, но не заменяет доказательство в изменении. Не заявлять о фактическом запуске, race или регрессии без статического основания; при недостатке обязательных материалов указать границу проверки по правилам REVIEWER.

## Что сознательно отброшено

Не делать самостоятельными замечаниями вкусовые требования без последствия: предел длины строки, форма `var`/`:=`, обязательный non-nil slice, число параметров, порядок деклараций или файлов, запрет reflection/ORM, обязательные именованные поля литерала. Также не навязывать table-driven тесты, `t.Parallel`, build tags, `goleak`, `testify`, `cmp` или конкретную структуру тестовых файлов. Это возможные решения, а не статически доказанные дефекты.
